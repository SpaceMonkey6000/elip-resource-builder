Reader 1 · the machine

The ATS isn't scoring you. It's parsing you — badly.

Workday, Greenhouse, Lever, Taleo, iCIMS — they're not robot judges handing out scores out of 100. They're parsing engines that dump your document into database fields. When the parse fails, your metrics turn to gibberish and you become invisible to the recruiter's search. Rejection by formatting, not by merit.

💀 What silently kills the parse

  • Two-column layouts. Parsers read left-to-right, so the sidebar merges into your job titles. Instant gibberish.
  • Skill bars & star ratings. The ATS reads zero data from graphics. Your "expert Python" becomes invisible.
  • Icon-only links. A GitHub logo with no URL text = the parser never sees your portfolio.
  • Headers & footers. Contact info up there is routinely ignored. Keep everything in the body.
  • Renamed sections. "My Journey" instead of "Experience" gets dropped into a text void.

✅ What parses clean, every time

  • One single column, top to bottom, summary to education.
  • Plain-text skills, comma-separated. The ATS indexes explicit lists heavily.
  • Spelled-out URLs for LinkedIn, GitHub, portfolio.
  • Standard headings: Summary, Experience, Education, Skills.
  • All content inside 1-inch margins — nothing in the header/footer zone.
File format & typography

The boring choices that decide if you're readable.

Font selection is a technical requirement, not an aesthetic one. On Linux-based ATS servers, "designer" fonts break — and a broken glyph breaks keyword matching.

FILE FORMAT

.docx is the safe default

.docx parses cleanly in 95–100% of cases across major platforms. Multi-column PDFs fail ~31% of the time. Text-based PDFs (exported from Word or LaTeX) are safe; image-based or design-software PDFs render blank to the parser.

SMART QUOTES

Kill the curly apostrophes

Word's "smart quotes" often render as question marks in an ATS, breaking word-boundary detection. Turn them off. Same energy as ligature bugs turning "Office" into "of?ce".

🅰️ Safe fonts (map perfectly)

  • Calibri
  • Arial / Helvetica
  • Times New Roman
  • Garamond
  • Inter · Computer Modern (LaTeX)

🅱️ Risky fonts (ligature bugs)

  • Montserrat, Poppins, Avenir — "fi"/"fl" break
  • Fira Code, JetBrains Mono & other mono "dev" fonts → broken fallbacks
  • Anything from a Canva graphic template
Lexical matching

The ATS is painfully literal. Mirror the job description.

"ReactJS" is not "React.js". "k8s" is not "Kubernetes". "JS" is not "JavaScript". The parser doesn't do synonyms — so use the exact terminology from the posting, and include both the acronym and the full term.

Spell out both

"Amazon Web Services (AWS)", "Continuous Integration / Continuous Deployment (CI/CD)". Capture every search.

A real Skills section

Mandatory. The ATS indexes an explicit comma-separated list far more heavily than skills buried in prose.

Context, not stuffing

Weave keywords into real bullets. White-text keyword stuffing is detected and penalized by modern teams.

Reader 2 · the human

The XYZ formula: the six-second weapon.

Popularized by Google recruiters and now the gold standard. STAR is too wordy for paper (35–45 words); PAR is too sparse (12–18). XYZ hits the sweet spot (18–25 words) and puts the number first — hooking the reader before they skim past.

🧪

Accomplished [X], as measured by [Y], by doing [Z].

✕ Task-based
"Built REST APIs using Spring Boot and MySQL."

Technically true. Utterly forgettable. No scale, no impact.

✓ XYZ-based
"Reduced search latency by 65% by implementing Elasticsearch caching, improving user retention by 12%."

Leads with the metric (Y), names the method (Z), ends with impact (X).

🚫 Passive openers reviewers penalize

  • "Responsible for…"
  • "Helped with…"
  • "Was involved in…"
  • "Assisted with…"

⚡ Strong action verbs

  • Engineered · Architected · Spearheaded
  • Optimized · Streamlined · Accelerated
  • Synthesized · Modeled · Forecasted
  • Orchestrated · Overhauled · Mitigated
No revenue yet? No problem

Measure the engine, not the sales.

Junior candidates and side-project builders rarely have user bases or revenue. So swap business metrics for technical metrics — they prove rigor just as convincingly.

Performance

"Reduced data rendering time by 20% by implementing WebSocket connections on a real-time dashboard."

Scale

"Architected a RESTful API handling 500+ concurrent requests using Node.js and JWT auth."

Quality

"Achieved 85% Jest coverage across 40+ components, cutting edge-case bugs before deploy."

🗂️

Build a "bullet vault": write 8–10 refined bullets per role, stack-rank them by impact, and deploy only the top few — swapping others in to tailor each application. The rest stay in reserve.

Level up any bullet

The 5-level system: from task to ownership.

Stack these layers to turn a flat task into a narrative of technical judgment.

1
The task

What you delivered

"Built an API." The raw feature or system.

2
Technique

The advanced practices

Pagination, rate limiting, concurrency models, CI/CD automation, design patterns.

3
Tools

The specific stack

Go, gRPC, Kafka, Kubernetes — the concrete languages and infra.

4
Method

How you worked

"Leading cross-functional RFC discussions," "in an Agile environment."

5
Metric

The XYZ payoff

Attach the measurable result to prove it mattered.

✕ Level 1 only
"Managed database migrations."
✓ All five levels
"Engineered and migrated a legacy SQL database to PostgreSQL using asynchronous batching, cutting query latency 40% and scaling to 25,000 concurrent users."
